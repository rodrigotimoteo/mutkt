# DSL reference

```kotlin
plugins { id("io.github.rodrigotimoteo.mutkt") }
mutkt { targetClasses.add("com.example.*") }
```

Requires the Java, Kotlin JVM or Android plugin. A test fails when this table drifts from the extension.

| Property | Type | Default | Meaning |
|---|---|---|---|
| `targetClasses` | List<String> | empty (all) | Class globs to mutate |
| `excludedClasses` | List<String> | `<generated>` (Android: also the generated-class globs below) | Class globs never mutated; `<generated>` skips classes compiled from generated sources (below) |
| `excludedMethods` | List<String> | empty | `method` or `pkg.Class#method` entries to skip |
| `operators` | Set<String> | empty (default operators) | Operator ids to enable, from [operators.md](operators.md); empty runs the six default-on operators, a non-empty set runs exactly those ids (list every id to run all); an unknown id fails the run and lists the valid ones |
| `threads` | Int | unset (available processors, resolved at run time) | Parallel test runs; more than the cores can cause false TIMEOUTs, since deadlines scale from a baseline run alone |
| `timeoutMs` | Long | 60000 | Upper bound of the per-mutant deadline in milliseconds; the baseline gets 5 × `timeoutMs` (300 s by default) |
| `maxMutantsPerClass` | Int | unset (unlimited) | Cap on mutants per class (omissions are shown in the summary, see below) |
| `failBelowScore` | Int | unset (no gate) | Minimum score in percent (0..100); the build fails below it |
| `failOnNewSurvivors` | Boolean | false | Fail the build on survivors that the committed `mutkt-baseline.json` does not accept (see [Survivor baseline](#survivor-baseline)) |
| `engines` | Set<String> | `junit-jupiter` | JUnit Platform engine ids to run (`junit-jupiter`, `junit-vintage`). With `junit-vintage`, a test runtime classpath without any vintage engine or JUnit Platform launcher (a `useJUnit()` build) gets MutKt's own vintage engine, so JUnit 4 tests need only `junit:junit`; the project's engine wins when it has one, and a project with its own launcher but no vintage engine fails the task with the dependency to add. Any other id must be on the test runtime classpath, otherwise the baseline run fails with the engine error |
| `includeTags` | Set<String> | empty | Only run tests matching one of these JUnit tag expressions (`fast`, `a & b`) |
| `excludeTags` | Set<String> | empty | Skip tests matching one of these JUnit tag expressions (`slow`, `!fast`) |
| `historyFile` | RegularFile | `build/mutkt/history.json` | Where results are kept between runs; a mutant whose code, covering tests and reached classes did not change keeps its result without running (see [Result history](#result-history)) |
| `variant` | String | `debug` | Android only: the variant whose classes are mutated and whose unit tests run against the mutants (`freeDebug` in a flavored build); a variant that does not exist or has no unit tests fails the build with the names of those that have them. AGP 9 gives unit tests to the tested build type only, so `release` needs `android.onlyEnableUnitTestForTheTestedBuildType=false` in `gradle.properties` |

`reports { }`:

| Property | Type | Default | Meaning |
|---|---|---|---|
| `console` | Boolean | true | Print the summary to the build log |

### Generated sources

`excludedClasses` starts with `<generated>`, which matches no class name: it skips each class whose compiled `SourceFile`, read under its package directory, is a file under the module's `build/generated` (where KSP, kapt, Java annotation processors and AGP write, so Room's `_Impl` classes and Moshi's `JsonAdapter`s) and no file of that name exists anywhere in the main source directories (when in doubt, the class is mutated). Nested and anonymous classes go with their file. `excludedClasses.add(...)` keeps it; `excludedClasses = [...]` (or `set`) without `<generated>` mutates those classes again. A class compiled without the attribute is never skipped this way. With `--info` the task logs how many classes it skipped.

### Android generated classes

With an Android plugin, `excludedClasses` starts with these globs, so classes the Android build generates are not mutated: `**.R`, `**.R$*`, `**.BR`, `**.BuildConfig` (resources and build config); `**.Hilt_*`, `**.*_HiltModules*`, `**.*_HiltComponents*` (Hilt); `**.*_*Factory`, `**.*_*Factory$*`, `**.*_MembersInjector`, `**.Dagger*Component`, `**.Dagger*Component$*`, `**.*Factory_Impl` (Dagger); `**.databinding.*Binding`, `**.databinding.*Binding*Impl`, `**.databinding.*Binding*Impl$*`, `**.DataBinderMapperImpl`, `**.generated.callback.*` (view and data binding); `**.ComposableSingletons$*`, `**.LiveLiterals$*` (Compose). `excludedClasses.add(...)` keeps them and adds yours; `excludedClasses = [...]` (or `set`) replaces them, and `excludedClasses = []` mutates everything. The globs go by name, not by annotation, so a user class that fits one is skipped too. The inexact ones: `**.R`, `**.BR` and `**.BuildConfig` match any class with that simple name; `**.*_*Factory` matches any class with an underscore that ends in `Factory` (`Api_V2Factory`); `**.databinding.*Binding*Impl` matches such a class in any `databinding` package. Apply the plugins in a `plugins { }` block: the globs are added when the Android plugin applies, so with legacy `apply plugin:` lines ordered MutKt, a `mutkt { excludedClasses = [...] }` block, then Android, they are appended to your value instead of being replaced by it.

### Result history

Each run stores its KILLED, SURVIVED and TIMEOUT results in `historyFile`, and the next run reuses a mutant's result instead of running it when nothing it depends on changed: its mutated bytes, the test classes that reached it in the baseline (with their nested and enclosing classes and their supertypes in the test sources) and every main class those test classes reached. Anything else that can change a result drops the whole history: the MutKt plugin itself, `operators`, `engines`, `includeTags`, `excludeTags`, `timeoutMs`, `threads`, the `test` task's JVM arguments, working directory and Java runtime, any jar or resource directory on the test runtime classpath, test-fixture classes, and test classes without test methods (shared fixtures, a base class with only `@BeforeEach`). The summary counts the reused results, `Mutants: 16 (12 reused)`, and the JSON report has `config.reused`; a reused result counts in the score like a fresh one. ERROR and NO_COVERAGE are never reused. The file is the task's local state, not an output: it never makes the task out of date, a build cache never restores it and `clean` deletes it. A file the task cannot parse fails it with `The MutKt result history <path> is corrupt (<detail>): delete it and run again`; one of another format version is ignored. Reach comes from the baseline, so a mutant that would send a test into a class the baseline never reached can keep a stale result after that class alone changes. Likewise a test class that calls helper code in another test class with tests of its own is not keyed on that class, and environment variables are not part of the fingerprint (CI changes some on every run), so a test that depends on one can keep a stale result. Delete the file to force a full run. To keep it on CI, see [getting-started.md](getting-started.md#keep-results-between-ci-runs); design and limits are in [ADR 0011](adr/0011-result-history.md).

### Survivor baseline

`./gradlew mutktUpdateBaseline` runs the same analysis as `mutkt`, with the same settings and `historyFile` (so right after `mutkt` it reuses every result) but without `failBelowScore`, and writes its survivors, the SURVIVED and NO_COVERAGE mutants, to `mutkt-baseline.json` in the project directory, replacing the file. Commit that file. Both tasks write `build/reports/mutkt`, so the reports show whichever ran last, and `./gradlew mutktUpdateBaseline mutkt` runs the update first. With `failOnNewSurvivors = true`, `mutkt` reads the file (it is an input of the task only then) and, after writing the reports, fails on survivors the file does not accept: `2 survivors are not in the MutKt survivor baseline <path>:`, their ids (at most 10) and `Kill them, or accept them with ./gradlew mutktUpdateBaseline`. A missing file accepts nothing. `failBelowScore` still applies on its own, and when both fail the message names both. An entry is a mutant id and a SHA-256 of its method's bytecode without line numbers, local variable names and frames, and a survivor is accepted only when both match. Unchanged code and edits that only move lines (comments, blank lines) keep every entry. Any other change to a method's code makes all of its survivors new, because the id numbers the sites of an operator within the method: a new site earlier in it takes the ordinal of an accepted survivor, so matching the id alone would accept a different mutant. A new survivor whose id was accepted reads `(accepted before its method changed: review it)`. A change that alters the bytecode without a source edit does the same: a Kotlin or Java compiler upgrade, an ASM upgrade in MutKt that reads the code differently, or an edit to an `inline` function, whose body is copied into each caller. Review those survivors and run `mutktUpdateBaseline` again. Renaming a method or class, or adding a lambda before another (kotlinc numbers them), changes ids, so those survivors are new too. The file holds the survivors of that run only, so running the update with a narrower `targetClasses` drops the others. A file that cannot be read fails the task with `The MutKt survivor baseline <path> is corrupt (<detail>): fix it or run ./gradlew mutktUpdateBaseline`. Design in [ADR 0013](adr/0013-survivor-baseline.md).

## Running

On Android, read `main` below as the `variant`'s classes and `test` as its unit-test task (`testDebugUnitTest`); see [getting-started.md](getting-started.md#android).

`./gradlew mutkt` (group `verification`) mutates the `main` classes and runs the `test` classes against each mutant in child JVMs that copy the `test` task's JVM arguments, system properties, working directory and Java launcher (the environment is inherited from the Gradle daemon). That launcher must be Java 17 or newer, since the child JVMs load MutKt's own Java 17 classes: on an older one (a JDK 8 or 11 toolchain) the task fails before any work with `MutKt runs the tests on the test task's Java launcher, which is Java 11 (<vendor> <version>), but needs Java 17 or newer`; the main code can still target an older Java. The child JVMs use the `test` task's own classpath, in its order, so entries added only to that task (a resource directory, for instance) are seen by the mutants' test runs and a change to them reruns the task. Classes of the project's other source sets on that classpath, as class directories or as their jar (`java-test-fixtures` fixtures, a shared test source set), load next to the main classes in the child JVMs, so a test that goes through them runs against the mutant; only the main classes are mutated, and a class name defined both in main and in such a source set fails the task. Another project's classes on that classpath (its test fixtures, for instance) load in the same class loader as the mutants, so a test that reaches the main classes only through them also runs against the mutant. The task is up to date until the classes, that classpath, the sources or these settings change, and it supports the configuration cache. An up-to-date run prints no summary. Coverage agents among the `test` task's `-javaagent` arguments (a jar name containing `jacoco`, `kover` or `intellij-coverage`) are not forwarded, so coverage never records mutant runs; other agents, such as a mocking library's, are. The summary is also written to `build/reports/mutkt/mutkt.txt`, next to `mutation-report.json` (Stryker mutation-testing-elements schema 2, sources included), `mutation-report.html` (one offline page that embeds the viewer and the report) and `mutation-report.sarif` (below); the task always writes all four and the directory is its declared output. It deletes the four files before it starts, so a run that fails before writing them (a red baseline, below) leaves no report from an earlier run. Statuses map to `Killed`, `Survived`, `Timeout`, `NoCoverage` and `RuntimeError` (ERROR, with its cause as `statusReason`); a survivor's `statusReason` is a one-line hint for its operator, such as `No test checks the value exactly at the boundary`; a killed mutant lists its first failing test in `killedBy` and its `statusReason` (`Killed by <test> (assertion)` or `(exception)`) says whether that test failed with an `AssertionError` or any other throwable, and every mutant lists the test classes that reached it in `coveredBy` (empty for NO_COVERAGE, absent when it ran every test class), each defined under `testFiles` so the viewer can show them. Bytecode has no columns, so a mutant spans the text of its line (at least one column). A mutant without line numbers, without a source file or with a line past the end of the file is placed on the first or last line. The HTML page carries a comment that points to the viewer's license and third-party notices, which ship in the `mutkt-report` jar. A cap omission is reported as `config.omittedByCap`. The summary groups survivors by method, the method with the most first, each with the test classes that reached it (at most three named, or `the whole suite`); it lists at most 10 methods and 5 survivors per method, names how many more there are (all are in the HTML report), and ends with a one-line hint per operator of the listed survivors. Each survivor shows the source lines around it when its file is found under the main source directories by the compiled `SourceFile` name (so `Prices.kt` for `PricesKt`, an `@file:JvmName` facade or a class in a differently named file): at `<package directory>/<name>`, else the only file with that name in all source directories. Several same-named files outside the package directory, no file, or a class compiled without the attribute show only the location. A `maxMutantsPerClass` cap keeps the first mutants of each class in discovery order. When it omits any, the score line reads `Score: 100.0% (1 evaluated, 2 omitted by the cap)`: evaluated counts every mutant that ran, ERROR included, and omitted counts the mutants left after `excludedClasses` and `excludedMethods` that the cap skipped. The score and `failBelowScore` use the evaluated mutants only. Mutants that ended in ERROR are listed after the survivors as `<mutant id>: <cause>` (the first line of the cause, at most 200 characters, for example a `VerifyError` or `exit code 7` of a child JVM that died before the tests started; one that dies after is KILLED by `JVM exit 7`, see the FAQ), at most 10 of them followed by `... and N more`. With `failBelowScore` set, the task fails with `Mutation score 62.50% is below the threshold of 80.00% (report: <path>)` when the score is lower; a score equal to the threshold passes, a value outside 0..100 fails the build, and a failed task is never up to date, so it fails again until the score or the setting changes. When no mutant is scorable (none generated, or all errored) there is no score: the build succeeds with a warning and `failBelowScore` is not applied. The tag filters and engines apply to every test run, so a mutant whose only killing tests are excluded survives, and one with no test left to run reports no coverage. Before any mutant is scored, a nonempty run first executes the selected tests once against the original classes in the same child JVM environment (its deadline is 5 times `timeoutMs`, since the JVM is cold). If a test or container fails there, or the run cannot start or times out, the task fails with `The tests fail on the original classes, so no mutant was scored: the first failure is <test>` (or the cause), leaves no report and applies no threshold, so an unrelated red test cannot count as a kill. A failure excluded by `excludeTags` or `engines` does not count, and a run with no mutants skips this step. That baseline runs on classes instrumented to record which test classes, and which Jupiter test methods, reach each mutant; a mutant then runs only those tests, in baseline order (a class that reached it outside its methods, in a `@BeforeAll` for instance, runs whole, and so does a class of another engine or one whose methods may depend on each other, see ADR 0010), and one that none reaches is NO_COVERAGE without a run (the FAQ lists the mutants that run every test class instead). If the instrumented classes fail the tests, the baseline runs again on the original classes, and only that run decides whether the task fails; when it passes, the task logs `The baseline on probed classes failed (<cause>); running every mutant against the whole suite`. The baseline also sets each mutant's deadline: 4 times the sum of how long its tests ran (plus, for a class that runs only some methods, its time outside them) and the longest test class's time (an allowance for class loading and shared set-up, such as a Spring context, that each run pays again), plus 4 s (4 times the whole suite's time plus 4 s for a mutant that runs every test class), at most `timeoutMs`, so an endless loop in a fast suite is cut within seconds. The factor covers mutants running `threads` at a time while the baseline runs alone. When `timeoutMs` cuts that deadline (tests that take more than about a quarter of it), slow kills and survivors can end in TIMEOUT, which counts as detected, so the task logs a warning as soon as the baseline ends and adds it under the score line: `Per-mutant deadline capped at timeoutMs (60.0s); the tests took 20.0s, so slow mutants may end in TIMEOUT: set timeoutMs to at least 84000`. The JSON report names the same values as `config.deadlineCappedAtMs`, `config.baselineMs` and `config.suggestedTimeoutMs` (rounded up to whole seconds). When every mutant ends in ERROR (mutants the JVM refuses to load, for instance) the task fails with `All N mutants ended in ERROR: none loaded or ran, see the report` after writing the report.

The child JVMs run the project's own JUnit Platform when its test runtime classpath has `junit-platform-launcher`, so a project on a newer Jupiter works. Gradle 8 injects the launcher into the `test` task only, so it is often absent from the classpath MutKt sees, and Gradle 9 does not inject it. When the test runtime classpath configuration (`testRuntimeClasspath`, or the Android variant's unit-test runtime classpath) has `org.junit.platform:junit-platform-engine` as a module (not as a plain file) and no launcher, `mutkt` resolves `org.junit.platform:junit-platform-launcher` at the engine's version from the project's repositories, without its dependencies. When it cannot (offline with an empty cache, or no repository has it), the child JVMs fall back to the Platform bundled with the plugin (1.10.2), which may be older than the project's engine, and the build logs a warning ending in `add testRuntimeOnly("org.junit.platform:junit-platform-launcher:<version>") to the dependencies` (with the configuration cache, only on the run that stores it). A run that gets MutKt's own vintage engine (see `engines`) resolves nothing and keeps the bundled Platform too. Declaring `testRuntimeOnly("org.junit.platform:junit-platform-launcher")` (it needs the JUnit BOM or an explicit version) skips the lookup. The project-on-another-version path is tested on Jupiter 5.11 / Platform 1.11 by `./gradlew :mutkt-junit:platformCompatTest` (needs the network, so it is outside `check`; run by its own CI job).

Class files read as resources inside the child JVMs (`Foo::class.java.getResourceAsStream("Foo.class")`) come back through a `mutkt-class:` URL, so libraries that require `file:` or `jar:` URIs for single class resources may not work.

It is not part of `check`. To opt in:

```kotlin
tasks.check { dependsOn("mutkt") }
```

### SARIF and GitHub annotations

`mutation-report.sarif` is a SARIF 2.1.0 log with one result per SURVIVED (level `warning`) and NO_COVERAGE (level `note`) mutant, at its source line; the tool is `MutKt` with one rule per operator id that has a result. A file's path is relative to `GITHUB_WORKSPACE` when that variable is set, else to the project directory. A mutant whose source file is not found under that directory (the same lookup as the survivor snippets) gets its package path instead (`demo/Calc.kt`), and one without line numbers has no region. When `GITHUB_ACTIONS=true`, the task also logs `::warning file=<path>,line=<n>,title=Survived mutant::<operator>: <description>` for each of the first 50 survivors (no `file` when the source is not found), then one `::notice` that counts the rest, so they show on the pull request diff. An up-to-date run logs none. See [getting-started.md](getting-started.md#github-actions) for a workflow.
