# DSL reference

```kotlin
plugins { id("io.github.rodrigotimoteo.mutkt") }
mutkt { targetClasses.add("com.example.*") }
```

Requires the Java or Kotlin JVM plugin. A test fails when this table drifts from the extension.

| Property | Type | Default | Meaning |
|---|---|---|---|
| `targetClasses` | List<String> | empty (all) | Class globs to mutate |
| `excludedClasses` | List<String> | empty | Class globs never mutated |
| `excludedMethods` | List<String> | empty | `method` or `pkg.Class#method` entries to skip |
| `operators` | Set<String> | empty (default operators) | Operator ids to enable, from [operators.md](operators.md); empty runs the six default-on operators, a non-empty set runs exactly those ids (list every id to run all); an unknown id fails the run and lists the valid ones |
| `threads` | Int | unset (available processors, resolved at run time) | Parallel test runs; more than the cores can cause false TIMEOUTs, since deadlines scale from a baseline run alone |
| `timeoutMs` | Long | 60000 | Upper bound of the per-mutant deadline in milliseconds; the baseline gets 5 × `timeoutMs` (300 s by default) |
| `maxMutantsPerClass` | Int | unset (unlimited) | Cap on mutants per class (omissions are shown in the summary, see below) |
| `failBelowScore` | Int | unset (no gate) | Minimum score in percent (0..100); the build fails below it |
| `engines` | Set<String> | `junit-jupiter` | JUnit Platform engine ids to run (`junit-jupiter`, `junit-vintage`); every id must be on the test runtime classpath, otherwise the baseline run fails with the engine error |
| `includeTags` | Set<String> | empty | Only run tests matching one of these JUnit tag expressions (`fast`, `a & b`) |
| `excludeTags` | Set<String> | empty | Skip tests matching one of these JUnit tag expressions (`slow`, `!fast`) |

`reports { }`:

| Property | Type | Default | Meaning |
|---|---|---|---|
| `console` | Boolean | true | Print the summary to the build log |

## Running

`./gradlew mutkt` (group `verification`) mutates the `main` classes and runs the `test` classes against each mutant in child JVMs that copy the `test` task's JVM arguments, system properties, working directory and Java launcher (the environment is inherited from the Gradle daemon). The child JVMs use the `test` task's own classpath, in its order, so entries added only to that task (a resource directory, for instance) are seen by the mutants' test runs and a change to them reruns the task. Classes of the project's other source sets on that classpath, as class directories or as their jar (`java-test-fixtures` fixtures, a shared test source set), load next to the main classes in the child JVMs, so a test that goes through them runs against the mutant; only the main classes are mutated, and a class name defined both in main and in such a source set fails the task. Known gap: another project's classes on that classpath (its test fixtures, for instance) that call this project's main classes still link to the unmutated main jar, so mutants reached only through them survive. The task is up to date until the classes, that classpath, the sources or these settings change, and it supports the configuration cache. An up-to-date run prints no summary. Coverage agents among the `test` task's `-javaagent` arguments (a jar name containing `jacoco`, `kover` or `intellij-coverage`) are not forwarded, so coverage never records mutant runs; other agents, such as a mocking library's, are. The summary is also written to `build/reports/mutkt/mutkt.txt`, next to `mutation-report.json` (Stryker mutation-testing-elements schema 2, sources included) and `mutation-report.html` (one offline page that embeds the viewer and the report); the task always writes all three and the directory is its declared output. It deletes the three files before it starts, so a run that fails before writing them (a red baseline, below) leaves no report from an earlier run. Statuses map to `Killed`, `Survived`, `Timeout`, `NoCoverage` and `RuntimeError` (ERROR, with its cause as `statusReason`); a killed mutant lists its first failing test in `killedBy`. Bytecode has no columns, so a mutant spans the text of its line (at least one column). A mutant without line numbers, without a source file or with a line past the end of the file is placed on the first or last line. The HTML page carries a comment that points to the viewer's license and third-party notices, which ship in the `mutkt-report` jar. A cap omission is reported as `config.omittedByCap`. Each survivor shows the source lines around it when its file is found under the main source directories by the compiled `SourceFile` name (so `Prices.kt` for `PricesKt`, an `@file:JvmName` facade or a class in a differently named file): at `<package directory>/<name>`, else the only file with that name in all source directories. Several same-named files outside the package directory, no file, or a class compiled without the attribute show only the location. A `maxMutantsPerClass` cap keeps the first mutants of each class in discovery order. When it omits any, the score line reads `Score: 100.0% (1 evaluated, 2 omitted by the cap)`: evaluated counts every mutant that ran, ERROR included, and omitted counts the mutants left after `excludedClasses` and `excludedMethods` that the cap skipped. The score and `failBelowScore` use the evaluated mutants only. Mutants that ended in ERROR are listed after the survivors as `<mutant id>: <cause>` (the first line of the cause, at most 200 characters, for example a `VerifyError` or `exit code 7` of a child JVM that died before the tests started; one that dies after is KILLED by `JVM exit 7`, see the FAQ), at most 10 of them followed by `... and N more`. With `failBelowScore` set, the task fails with `Mutation score 62.50% is below the threshold of 80.00% (report: <path>)` when the score is lower; a score equal to the threshold passes, a value outside 0..100 fails the build, and a failed task is never up to date, so it fails again until the score or the setting changes. When no mutant is scorable (none generated, or all errored) there is no score: the build succeeds with a warning and `failBelowScore` is not applied. The tag filters and engines apply to every test run, so a mutant whose only killing tests are excluded survives, and one with no test left to run reports no coverage. Before any mutant is scored, a nonempty run first executes the selected tests once against the original classes in the same child JVM environment (its deadline is 5 times `timeoutMs`, since the JVM is cold). If a test or container fails there, or the run cannot start or times out, the task fails with `The tests fail on the original classes, so no mutant was scored: the first failure is <test>` (or the cause), leaves no report and applies no threshold, so an unrelated red test cannot count as a kill. A failure excluded by `excludeTags` or `engines` does not count, and a run with no mutants skips this step. The baseline also sets each mutant's deadline: 4 times how long its tests ran plus 4 s, at most `timeoutMs`, so an endless loop in a fast suite is cut within seconds. The factor covers mutants running `threads` at a time while the baseline runs alone. When `timeoutMs` cuts that deadline (tests that take more than about a quarter of it), slow kills and survivors can end in TIMEOUT, which counts as detected, so the task logs a warning as soon as the baseline ends and adds it under the score line: `Per-mutant deadline capped at timeoutMs (60.0s); the tests took 20.0s, so slow mutants may end in TIMEOUT: set timeoutMs to at least 84000`. The JSON report names the same values as `config.deadlineCappedAtMs`, `config.baselineMs` and `config.suggestedTimeoutMs` (rounded up to whole seconds). When every mutant ends in ERROR (mutants the JVM refuses to load, for instance) the task fails with `All N mutants ended in ERROR: none loaded or ran, see the report` after writing the report.

The child JVMs run the project's own JUnit Platform when its test runtime classpath has `junit-platform-launcher`, so a project on a newer Jupiter works; without it they fall back to the Platform bundled with the plugin (1.10.2), which may be older than the project's engine. Declare it with `testRuntimeOnly("org.junit.platform:junit-platform-launcher")` (it needs the JUnit BOM or an explicit version). Gradle 8 injects the launcher into the `test` task only, so it is often absent from the classpath MutKt sees; Gradle 9 does not inject it, so a Jupiter project on Gradle 9 must declare it. The project-on-another-version path is tested on Jupiter 5.11 / Platform 1.11 by `./gradlew :mutkt-junit:platformCompatTest` (needs the network, so it is outside `check`; run by its own CI job).

Class files read as resources inside the child JVMs (`Foo::class.java.getResourceAsStream("Foo.class")`) come back through a `mutkt-class:` URL, so libraries that require `file:` or `jar:` URIs for single class resources may not work.

It is not part of `check`. To opt in:

```kotlin
tasks.check { dependsOn("mutkt") }
```
