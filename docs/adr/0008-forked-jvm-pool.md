# 0008 Forked JVM pool instead of WorkerExecutor

## Context

ROD-104 asked for `WorkerExecutor.processIsolation`. The Gradle 8.10 Worker API cannot kill a running worker: `WorkQueue` has only `submit` and `await`, and `WorkAction.execute` returns void (checked with javap on gradle-api-8.10.jar). A hung mutant (infinite loop) therefore cannot be stopped.

## Decision

`RunMutationAnalysis` stays in the Gradle daemon. A plugin-owned pool of child JVMs, started with `ProcessBuilder` from the task action, runs mutants through a length-prefixed frame protocol. The child answers a run with a `Started` frame once classes are loaded and linked and the tests discovered (discovery of all test classes counts against the preparation limit, so a stall there is caught by it; the plans are held until the run ends, a known cost until ROD-135), then with the result. The parent calls `destroyForcibly()` on a child and starts a replacement when it is silent for deadline plus grace after `Started` (TIMEOUT, counted as detected, ADR 0002) or for the preparation limit before it (60 s by default; the run throws, so the mutant is ERROR and earns no detection credit). A child that exits after `Started` is a kill by the mutant (ADR 0002) and is replaced; one ended by a signal is ERROR. A reused child can still run a stray thread from an earlier mutant (one a test started and never stopped); if that thread exits the JVM, the current mutant gets the kill, a rare misattribution accepted to keep children reused. Children are not reused when the classpath has Robolectric, which caches the project classes it loaded in JVM-wide statics (ROD-223). A baseline asked for coverage runs on the instrumented classes, which the parent writes to a directory named in the request, and the child reads and clears their probe arrays after each root test class without initializing any class; with Robolectric it reads none, since its sandbox loader defines the project classes again (ROD-239). Each run loads the dependency jars in its own class loader, which a library thread or static can keep reachable (ROD-234), so a child whose Metaspace is over 512 MiB or whose heap is over 75% of its maximum after a run, still so after a GC, asks in its result not to be reused. A reused child that runs out of memory or time may do so from what earlier runs left behind, so that mutant runs once more on a fresh child, whose outcome counts (ROD-236); a real TIMEOUT on a reused child therefore costs up to two deadlines, never more. 3 runs in a row with no `Started` within the preparation limit, or 3 failed starts in a row, stop the analysis: the executor throws `TestExecutionStopped` and the task fails with its message (naming the limit and the last child output), since every later mutant would fail the same way. JVM args, system properties and launcher are copied from the Gradle `Test` task.

## Consequences

- Criterion "daemon memory unaffected" is verified as child pid != daemon pid.
- Memory cost is N children times the test heap.
- Status: accepted under owner autopilot, pending owner confirmation. The change is reversible and sits behind the `TestExecutor` port.
